# WanderPlan 0.9.0 — Unequal expense splits (R10)

Each expense now has **Cách chia**: **Chia đều** (default, unchanged), **Theo phần** (e.g. A 2 phần, B 1 phần, with a live per-person preview) or **Theo số tiền** (exact đồng per participant). The expense list shows the split ("Chia theo phần A ×2, B ×1" / "Chia theo số tiền A 250.000 ₫, B 50.000 ₫") and **Ai cần trả cho ai?** uses it.

Customer rules (16/10/2026): exact amounts must total the actual amount, or the estimate while no actual exists; when they no longer match (for example after entering the actual amount) saving is blocked and the difference is shown until the split is re-entered. With shares, leftover đồng go to the payer when the payer participates, otherwise one each in the existing fixed order. Excel adds **Cách chia** and **Chi tiết chia** (`email: 2; email: 1` or `email: 150000; …`); files without these columns import new rows as equal and keep the saved split of updated rows.

## Verification

- 103 application tests across 22 suites; lint and production build passed.
- 240 SQL assertions across 13 suites on embedded PostgreSQL and full local Supabase. New tests cover shares/amounts persistence, mismatch against actual/estimate, missing or zero shares, values for non-participants, unknown method, edited actual without new amounts, direct amount/participant edits, old clients unable to reset an unequal split, switching back to equal and Excel import.
- Two-account local UAT: owner created a 2:1 share split (preview 200,000/100,000) and the member saw it plus the updated settlement through Realtime; the member switched to exact amounts, a 10,000 ₫ shortfall was blocked, the corrected split saved and the owner's settlement updated; changing the actual amount without re-entering amounts was blocked. 320/375 px dialogs: no overflow, 47 px inputs. UAT data restored.
- UAT found that switching from shares to amounts reused the share inputs' values; fixed with a failed-before/passed-after regression test.
- ITS on the local stack: forged share values on direct participant writes and a direct method change are rejected at commit; anonymous execution denied. Scoped simplify review applied.

## Rollout and recovery

Apply only the additive migration `20261016220000_unequal_expense_splits.sql` before the frontend. Existing expenses become `equal` with no values; no data changes. The save RPC keeps its parameters plus two optional ones, so an older cached frontend still saves equal expenses but is refused (not silently reset) when editing an unequal one. Prefer forward repair; do not replay historical migrations.

Limits: Excel round trip verified by unit tests and the import RPC, not by a browser file upload. Hosted authenticated Realtime/email and a real Google OAuth round trip remain untested; production verification is read-only.
